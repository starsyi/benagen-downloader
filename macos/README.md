# macOS 客户端（BenagenDownloader）—— 手工验收清单

这一份是**给人看的**验收清单：把 `.app` 打开，照着 1–22 条点一遍
（外加第 23 条：诊断日志怎么开、怎么导、导出来长什么样）。
它和自动化测试是**互补**的两件事，不是重复：

| | 自动化（`bash macos/scripts/e2e_shell_macos.sh`） | 本清单 |
|---|---|---|
| 覆盖 | 真内核 + 真 aria2c + 桩服务，整条链路（清单 → 入队 → 落盘 → 校验 → 收尾） | 屏幕上**看得见**的东西：窗口、文字、角标、面包屑、Finder 定位 |
| 判据 | 断言（会红会绿） | **每一条都写了"怎么看算通过"** |
| 为什么缺不了 | —— | `.labelStyle(.titleAndIcon)` 被删掉这类回归**没有任何自动化判据**，只有眼睛能发现 |

> ⚠️ **三条本清单特有的性质，先读再动手：**
>
> - **第 13 条是"对照探针"，不是第 12 条的复述。** 第 12 条问"退出后有没有孤儿"，
>   第 13 条问"第 12 条的通过**到底证明了什么**"。两条的结论都要写下来。
> - **第 16 条是已知缺口的告知，不是通过项。** 它现在就该是坏的，**不要去修它**。
> - **第 15 条本机很可能复现不出来。** 复现不出就**如实写「未验证」**，
>   **绝不要**写成「已验证」，也**不要去改本机系统隐私设置**来人为复现（那要先问人类伙伴）。

## 0. 准备

```bash
# 构建（内核 + 壳 + 打包），产物在 macos/dist/BenagenDownloader.app
bash macos/scripts/build_app_macos.sh

# 打开（也可以直接在访达里双击）
open macos/dist/BenagenDownloader.app
```

需要的东西：

- **一条真实交付码**（20 位，或邮件里那条完整链接）。第 2–8b 条要靠它。
  没有可用的交付码时，这几条只能记「未验证」——**不要**拿一个编出来的码去"验证"。
- **下载目录是 `$HOME/Downloads/Benagen`**（内核的默认值，界面上**没有**这一项、
  壳也不传 `--download-dir`）。第 2–8b 条会在那里落真实文件。
- 第 14 条要断网；第 15 条要一台**没授权过**的机器。

> ⚠️ **别把 `macos/scripts/e2e_shell_macos.sh` 的输出当成这份清单的替代。**
> 那条脚本第 1 步跑的是**临时目录**里的桩服务与夹具，碰不到 `~/Downloads`；
> **但第 3 步的启动取证会真起一次 `.app`**（`$HOME/Downloads/Benagen` 是它的下载目录，
> 而且它会**自动加载内核记住的交付码** —— 详见脚本头部那段"边界"），
> 也**一个界面判据都不覆盖**。

## 0b. 出 Intel（x86_64）包

本阶段出**两个独立包**（人类伙伴的决定：不做通用二进制）：Apple Silicon 一份、Intel 一份。
Intel 那份**一条命令**：

```bash
bash macos/scripts/build_app_macos.sh x86_64     # 内核 + 壳 + 打包，三个二进制都是 x86_64
bash macos/scripts/build_dmg_macos.sh            # → macos/dist/BenagenDownloader-Intel.dmg
```

arm64 那份就是原来那条——**不带参数**，行为与阶段 F 之前逐字相同：

```bash
bash macos/scripts/build_app_macos.sh            # → 三件都是 arm64
bash macos/scripts/build_dmg_macos.sh            # → macos/dist/BenagenDownloader-AppleSilicon.dmg
```

`build_dmg_macos.sh` **没有架构参数**：它把包内三个二进制逐个 `lipo -archs` 读出来，
据此决定产物名。于是"名字说 Intel、里面其实是 arm64"在结构上不可能发生；包要是通用二进制
（两个架构）或混架构，它**拒绝出包**（本阶段不做通用包，它也没法被命名成其中一个）。

两个架构各自的全流程验收（内核 + 真 aria2c + 桩服务 + 打包 + 启动取证）：

```bash
bash macos/scripts/e2e_shell_macos.sh            # arm64
bash macos/scripts/e2e_shell_macos.sh x86_64     # Intel（先读下面几节）
```

### 部署目标（最低系统版本）：**四个声明各在一处，改一个不够**

包能不能在目标机型上打开，由**四个**下限声明共同决定，而它们**分属四个不同的地方**：

| 声明 | 写在哪 | 谁决定它 |
| --- | --- | --- |
| `Info.plist` 的 `LSMinimumSystemVersion` | 组装时生成 | `build_app_macos.sh` 的 `MIN_MACOS` |
| 壳 `BenagenDownloader` 的 `minos` | Mach-O 头 | `macos/Package.swift` 的 `platforms:` |
| `benagen-core` 的 `minos` | Mach-O 头 | `core/` 的 Rust 构建（与上面两个无关，实测 11.0） |
| `aria2c-macos-<架构>` 的 `minos` | Mach-O 头 | `downloader/scripts/build_aria2_macos.sh` 的 `MIN_MACOS` → `-mmacosx-version-min` |

🔴 **`MIN_MACOS` 只写得到第一行**：它**碰不到任何二进制的 Mach-O 头**。所以
`MIN_MACOS=13.0 bash build_app_macos.sh x86_64` 单独用是个**假的修复**——plist 说 13、
壳却还是 14，装到 13 上照样打不开，而且**整条链没有一步会报错**。

**这个坑真实发生过**（2026-09-20）：客户在 **macOS 13.7.8 Intel** 上双击
`BenagenDownloader-Intel.dmg`，得到「应用程序的这个版本不能与此版本的 macOS 配合使用」。
当时实际是壳 `minos 14.0` + `aria2c minos 26.0`（构建机是 macOS 26、编译时没给版本标志），
只有 `benagen-core` 的 `11.0` 合格。当前两份包都按 **13.0** 重出。

**判据**（读不出来也算失败，会当场判死）：

```bash
bash macos/scripts/check_minos_macos.sh macos/dist/BenagenDownloader.app 13.0
```

它读 plist + 三个二进制的 Mach-O 头（`LC_BUILD_VERSION` 的 `minos` 与旧形态
`LC_VERSION_MIN_MACOSX` 的 `version` **两种都认**，版本比较是**数值**比较——
`10.12 ≤ 13.0` 字符串比会错判）。`build_app_macos.sh` 与 `build_dmg_macos.sh`
都会在出包前自动调它 ⇒ **下限不对就不出包、不装盘**，"只跑 DMG 脚本把旧包装盘"也漏不掉。

⚠️ **`lipo -archs` 对这件事是瞎的**：事故当时三个二进制的架构与名字全对，
所以既有那五条判据一条都不红。这是本条判据存在的理由。

**要改下限时，四处一起动**（当前 13.0）：
1. `macos/Package.swift` 的 `platforms:`（壳）；
2. `macos/scripts/build_app_macos.sh` 的 `MIN_MACOS` 默认值（plist）——
   `build_app_macos.sh` 会断言它与 `Package.swift` **一致**，不一致直接不出包；
3. `downloader/scripts/build_aria2_macos.sh` 的 `MIN_MACOS` 默认值（aria2c），
   **两个架构都要重编**（切架构时若壳的 minOS 不对，先删
   `macos/.build/out/Products/Release/BenagenDownloader`）；
4. 重编 aria2c 会改内嵌摘要 ⇒ 跑 `cd core && cargo build --release` 同步
   `core/assets/`，更新 `core/src/engine/daemon.rs` 的 `ARIA2C_EMBED_SHA256`
   （**两个架构各一个字面量**），再跑 `cargo test` **与**
   `cargo test --target x86_64-apple-darwin`。

⚠️ **降下限解决的是"装不装得上"，不是"在旧系统上跑不跑得起来"**——
后者只有真机验得到，见下面《只能真机的部分》。

### 前置：x86_64 需要 **rustup 那份** cargo

x86_64 的 std 不在 Homebrew 的 rust 里。**每次**构建 Intel 包之前：

```bash
export PATH="$HOME/.cargo/bin:$PATH"     # 让 rustup 的 cargo 排到 Homebrew 的前面
```

漏了这句时 `build_app_macos.sh x86_64` 与 `e2e_shell_macos.sh x86_64` 会**在编译之前**
立刻失败，并把完整配方整段打出来（`core/scripts/preflight_x86_64_toolchain.sh`，
含一次性安装步骤）——**不会**静默降级成"编一个 arm64 包、管它叫 Intel 包"。

### 产物架构是自己验的（不听参数）

`build_app_macos.sh` 组装完之后把包里三个二进制（壳 / `benagen-core` / `aria2c-macos-<架构>`）
逐个 `lipo -archs`，任何一个不等于目标架构就**大声失败、包不做出来**；`e2e_shell_macos.sh`
与 `build_dmg_macos.sh` 各自再验一遍（后者验的是**从 DMG 里读回来的**字节）。
理由是实测的：`arch -x86_64 clang` **仍然编出 arm64**——"参数传对了"证明不了任何事。

### 只能真 Intel 验的四件事（诚实的边界）

出这个包的机器是 Apple Silicon，**所有 x86_64 运行都经 Rosetta 翻译**。下面四件本机
**一件都验不了**，必须在目标 Intel 机器上过一遍：

| # | 验什么 | 为什么本机验不了 |
| --- | --- | --- |
| 1 | **真实 HTTPS 下载链路**：用真交付码从 `download.benagen.com` 下完一批、六类校验全绿 | 本机 e2e 走的是 `python3 -m http.server` **桩**（HTTP、本机回环），没经过真实 TLS |
| 2 | **SecureTransport 握手** | aria2c 用的是 `AppleTLS`（SecureTransport，无 OpenSSL）。x86_64 的握手路径在本机是 Rosetta 翻译执行的，与原生 Intel 不是同一条 |
| 3 | **Gatekeeper / quarantine**：经浏览器下载 → 双击 → **按系统版本走放行流程**（见下） | 本机构建产物**不带** `com.apple.quarantine`，那条链路复现不出来。⚠️ 而且**这一步对两个架构是一样的**（见下），别以为 Intel 那份"更麻烦" |
| 4 | **下限声明在旧系统上的实际行为**（能否装上、能否起来、引擎能否真的执行） | 本机能验的只有"**声明的**下限"（静态读字节）与"编译期没有未加保护的 14+ API"——**必要不充分**。见下面《只能真 macOS 13 验的》 |

#### 第 3 条的展开：放行流程**按系统版本分**，两个架构**完全一样**

「右键 →「打开」」这条老办法**从 macOS 15 Sequoia 起已经失效**（Apple 移除了那条路），
照着念会让客户卡在"我右键了但没这个选项"：

- **macOS 15 及以上**：先**双击一次**（会被拦下、弹"无法打开"）→ 系统设置 →
  「隐私与安全性」→ 在"安全性"里找到那条拦截记录 → 点「**仍要打开**」→ 再确认一次。
  ⚠️ 那个按钮**只在尝试打开之后的约 1 小时内可用**；隔太久就再双击一次、回系统设置里点。
- **macOS 14 及以下**：右键（或按住 Control 点击）→「打开」→ 再确认一次。

> **盘里还有一个现成的办法：`已损坏修复.command`。** 客户不想照着上面点几步的话，
> 双击它就完事 —— 它把应用装进 `/Applications`、清掉 `com.apple.quarantine`、再启动。
> 它**不碰系统 Gatekeeper**（`spctl --master-disable` 那种做法既危险又**没用**，
> 实测证据见 **附 G**）。源码在 `macos/Resources/已损坏修复.command`，
> `build_dmg_macos.sh` 装盘时拷进去，并在挂载自验里判一次。

**为什么两个架构一样**：ad-hoc 签名**不是** Developer ID，而 Gatekeeper 只认
Developer ID + 公证 ⇒ 带 quarantine 时，"ad-hoc 签名的 arm64"与"完全不签的 x86_64"
**是同一个结局**（都被拦一次、都走上面那条流程）。
两者唯一真正的差别是：**arm64 上"有 ad-hoc 签名"是内核的执行要求**（不签根本起不来，
链接器会自动补上），x86_64 **不要求**（`codesign -dv` 报 `not signed at all` 也照跑）。
⇒ 准确的说法是「**Intel 那份执行不受影响、安全姿态并不更强**」，**不是**"Intel 那份更坏"。

> **本机已经验到的**（Rosetta 当武器，报告里都有原始输出）：x86_64 内核在 Rosetta 下真跑、
> 真起 **x86_64 的 aria2c**（用内核释放出来的引擎缓存 `aria2c-<内容哈希>` 取证，哈希与
> `core/assets/aria2c-macos-x86_64` 逐字相同）；完整 e2e（清单 → aria2 → 落盘 → 校验）全绿；
> Intel `.app` 真起窗口（`lsappinfo` 报 `Arch=x86_64`）；两张 DMG 都能挂载、盘内架构与名字一致。

### 只能真 **macOS 13** 验的（2026-09-20 那轮移植新增）

🔴 **"本机跑得起来"推出不了"13 上也能跑"——这次事故本身就是它的反例**：
上面那段"本机已经验到的"在**事故之前**就全绿了（x86_64 内核在 Rosetta 下真跑、完整 e2e 全绿、
Intel `.app` 真起窗口），而客户那台 macOS 13.7.8 上**连窗口都打不开**（壳 14.0 / aria2c 26.0）。

本机能证明的只有两件事：**声明的下限**（静态读字节，`check_minos_macos.sh`）与
**编译期没有未加保护的 14+ API**（部署目标 13 下那是编译错误）。**必要，不充分。**
下面三类本机照不到：

1. **弱链接符号**：`-mmacosx-version-min` 只改声明、不改"调了哪些符号"。某个只在 14+ 的符号会被
   记成 weak import ⇒ 在 26 上正常解析、**在 13 上拿到 NULL 就崩**。编译期能挡多数，
   挡不住 **libc++ 新增符号**（aria2c 是 C++，**这是本次最高的残留风险**）、
   字符串 selector / KVC、泛型特化。
2. **系统行为按版本分**：aria2c 走 **AppleTLS / SecureTransport**；`~/Downloads` 的
   **TCC 授权框**（握手超时那整条设计就是为它写的）；Gatekeeper / quarantine。
   26 与 13 **不是同一条实现路径**。
3. 本机所有 x86_64 执行都经 **Rosetta 翻译**，客户的 Intel 是**原生**执行。

**真机清单**（按此顺序，在 macOS 13.7.8 Intel 上）：

| # | 做法 | 通过的判据 |
| --- | --- | --- |
| 1 | `sw_vers` 确认是 13.7.8；DMG 双击挂载 → app 拖进「应用程序」 | 挂得上、拖得进 |
| 2 | 放行：**右键（或 Control+点击）→「打开」** | 13 走的是这一支（"双击一次→去系统设置点仍要打开"是 **15+** 的流程，见上面第 3 条） |
| 3 | 双击 | **不再**出现「应用程序的这个版本不能与此版本的 macOS 配合使用」；窗口出现；工具栏三段**文字**在（不只图标） |
| 4 | 🔴 **aria2c 真的执行**（最关键） | 加载一批 → 下载任一文件 → 传输列表进度**在动** → 文件落到 `~/Downloads/Benagen`；`pgrep -fl aria2c` 有命中 |
| 5 | 设置窗口的**两个入口**都点一遍：`⌘,` 与工具栏那颗 | 都开得出来。⚠️ 这是 `SettingsEntry` 里 `if #available` 的 **13 分支**，开发机（26）**永远走不到** |
| 6 | 6 处 `onChange` 的行为 | 换成另一个码 ⇒ 回根、勾选面清空；同码重载 ⇒ 下载回执消失但**所在子目录与勾选面不变**；切到传输列表开始刷、切走停止；设置里保存参数 ⇒ 表单被回执重填；换码面板备注敲一半 → 点别处/关面板 ⇒ **不丢** |
| 7 | 🔴 **失效粒度回归**（本轮唯一新增的运行时风险） | 让下载在跑（200 ms 轮询在跑）→ 打开换码面板 → 在某行备注里**连续快速打字** ⇒ **字不丢、光标不跳、每敲一个字都上屏** |
| 8 | 退出应用 | `pgrep -fl benagen-core` 与 `pgrep -fl aria2c` **都为空** |

第 7 条为什么单列：模型层从 `@Observable` 换成了 `ObservableObject`（13 上没有 Observation 框架）。
`@Observable` 对**等值**写入会**抑制**通知，`@Published` **不会** ⇒ 传输列表每 200 ms 一次的轮询
会变成每拍都发全局失效。三处写护栏（`engine` / `lastError` / `protocolAlerts`）就是为此加的，
但它们只覆盖已知的三处，**这条回归只能靠人在真机上试**。

⚠️ 客户机上多半**没有** `vtool` / `otool` / `codesign`（没装 Command Line Tools）——
真机能用的判据只有**行为**，别指望客户帮你读 Mach-O。

## 1. 双击 `.app` → 窗口打开、无 Gatekeeper 拦截

**做法**：在访达里找到 `macos/dist/BenagenDownloader.app`，**双击**（不是 `open` 命令）。

**怎么看算通过**：

- 窗口出现，标题栏写着 **「Benagen 数据下载工具」**，尺寸约 1100×720；
- **没有**"无法打开，因为来自身份不明的开发者"这类弹窗；
- 终端里 `xattr -l macos/dist/BenagenDownloader.app` **看不到 `com.apple.quarantine`**
  （`com.apple.provenance` 是正常的，不是隔离属性）。

**为什么还要人眼看**：`verify_app_launch_macos.sh` 已经用两路取证（`lsappinfo` 的
`Foreground` + CoreGraphics 的真窗口）证明"窗口真的开了"，但它走的是 `open`，
**不是**访达里的那一下双击。而 Gatekeeper 的判定与"文件从哪来"有关，
双击才是客户真实的那条路。

> 本机构建的产物**不带** quarantine，所以不该被拦。
> **"客户从浏览器下载 → 首次打开点穿弹窗"那条链路本阶段未实测**
> （交付页的 Gatekeeper 指引沿用上一阶段，见设计规格 §11）。

## 2. 输入交付码 → 看到批次摘要与文件树，文件名里的 `×` 与空格原样显示

**做法**：把交付码（或完整链接）粘进空态页的输入框 → 点「加载」。

**怎么看算通过**：

- 侧边栏「文件」那一屏出现**批次摘要**（交付码、文件数、总大小、有效期）与**文件树（平铺列表）**；
- **文件名里的 `×`（乘号）与空格原样显示**——例如 `C24-8_×_25WS024`、`QC 图.png`。
  **不得**出现 `%C3%97` / `%20` / `Ã—` 这类形态；

  > 这条不是形式主义：内核按清单原文落盘、壳按原文渲染（约束 3）。
  > 一个"顺手解码/编码一下"的实现会把中文名变成乱码，而**它不影响任何数字**，
  > 所以自动化很难抓到。真交付里这种名字是常态，不是特例。
- 加载期间界面**不冻死**（可以切分区、可以滚动）；长加载（实测约 91.5 秒）内也不许转圈卡住。

**已知行为，别误判**：`×` 在**列表行的排布里**可能被中间截断（长路径、窄窗口）。
完整原文在悬停提示里。只要**没有变成 `%C3%97` 这种编码形态**就算通过。

## 11c. 换批时的调用序（潜在的静默，纯值单测按构造抓不到）

**做法**：加载批次 **A** → 换到批次 **B** → **不点任何东西** → 立刻换回 **A** →
看底部状态栏的「已选 N 项」。

> 🔁 **复现条件（不写清楚这条会给出假通过）**：危险的那条调用序只在
> **"视图首帧晚于 `get_tree` 返回"**时才成立 —— `AppModel` 是**先落**
> `loadState = .loaded(info)`（`AppModel.swift` 的 `performLoadDelivery`），
> **之后**才 `await getTree()`（同段末尾那行，中间隔着一个网络往返）。
> 在大批次 / 慢机器 / 第一次渲染要做的活多时更容易撞上；小批次 + 快机器上
> 可能**一次都撞不到**，那时"看着通过了"其实**没有验到这一条**。
> 复现不出就如实记「未复现」，**不要**写成「已验证」。
> （换句话说：这一条的**真正守卫是代码审阅**——`RootView` 的 `.onChange` 与
> `FileBrowser` 的 `.task(id:)` 之间没有顺序保证这件事，看一眼那两个块就知道还在不在。）

**怎么看算通过**：

- 回到 A 后，**默认选中面被重新播下来**（N = A 的默认选中项数，**不是 `已选 0 项`**）；
- 顺带：在同一个批次里进目录再返回，**用户自己攒的勾选不该被清掉**。

**为什么**：`RootView` 的 `.onChange`（换批复位）与 `FileBrowser` 的 `.task(id:)`（播种默认面）
在 SwiftUI 里**没有顺序保证**。若某一拍"播种"先跑、"复位"后跑，复位会把刚播下的面清掉，
而 `taskKey` 的三个分量都没变 ⇒ 不会重进 ⇒ 用户看到「已选 0 项」且**没有任何提示**。

> **若复现出来：停下、记录下来、上报**——**不要就地打补丁**。
> （这不是任务 7 引入的，旧实现同一调用序下症状相同；任务 7 之后曾经多一个次生症状：
> 记账被清成 `nil` 后，同批内任何一次 `taskKey` 变化都会**重播默认面、抹掉用户攒的选择**。
> **阶段 D 之后这个次生症状被收窄了**：播种的记账改成了「已经为**哪一次加载**播过种」
> （`ManifestTracking.seededGeneration`），同一代里的任何 `taskKey` 变化都不再重播 ——
> 而"哪一次加载"这件事只有一次成功的 `load_delivery` 能推进，界面上没有别的写入点。）

## 11d. 下载结果提示条

**做法**：点一次「下载选中」或「全部下载」；然后切到别的分区再切回来；再**成功加载一次**
（换一个新码，或者用换码面板**重新提交当前这个码**）；最后再做一次**失败**的加载
（输一个不存在的码）。

**怎么看算通过**：

- 主区上方**出现结果提示条**（"已加入 N 个下载任务"；有批内文件都已完整时是
  **"没有需要下载的文件"**——见下面那一条；有被拒的文件则**逐条**列出路径与原因）；
- **切到别的分区再切回来，它还在**（约束 4：拒绝理由不能因为用户切了视图就消失）；
- **一次成功的加载之后它被收起**（换批 / 同码重载都一样）—— 内核已经重新规划过整批，
  那条回执描述的状态不存在了。**这是有意为之**：约束 4 要的是"失败不许自己消失"，
  不是"旧结论可以永远冒充现状"（理由与代价写在 `RootView.body` 那条
  `.onChange(of: model.loadGeneration)` 上）；
- ⚠️ **一次失败的加载之后它必须原样还在**（约束 4 的另一半）：上面最后那一步里，
  输入一个不存在的码 → 加载失败 → 那条拒绝理由**一个字都不能少**。
  若它消失了，就是回归（`aFailedLoadDoesNotAdvanceTheLoadGeneration` 在模型层守着这条）；
- `added` 非空时**自动切到传输列表**；一个文件都没加进去时**留在原地**把理由说清楚。

> **"没有需要下载的文件"**（阶段 D 的 D-2）：勾选面为空（= 工具栏/底栏的「全部下载」）
> 且内核算出的待下载集合为空时，内核回的是**成功 + `added` 空数组**，不再是
> `invalid_params("没有匹配到任何文件")`。**这句话是壳自己写的** —— 内核在这条路上
> 一个字都没说（它不是错误、没有 `message` 可登），而"点了下载、界面什么都不说"
> 是约束 4 明禁的静默失效。措辞只陈述事实，不加判断、不加建议（理由写在
> `EnqueueFeedback.of` 上）。**验收**：把一个批次的文件全部下载完（或删掉后重下到全部完整），
> 再点一次「全部下载」→ 出现的就是这一句，**不是**一句报错。

**做法**：

1. 先按第 12 条正常 ⌘Q 退出，确认 `pgrep -fl 'benagen-core|aria2c'` 为空；
2. 重新打开应用（`open macos/dist/BenagenDownloader.app`），**先确认内核起来了**：
   `pgrep -fl benagen-core` 有输出；
3. `kill -9` **强杀壳进程**（不给 `applicationWillTerminate` 任何机会）：

   ```bash
   pkill -9 -f 'BenagenDownloader.app/Contents/MacOS/'
   sleep 3
   pgrep -fl 'benagen-core|aria2c'
   ```

**怎么读结果**（两种情形都要如实写下来）：

- **情形 A：强杀后内核也立刻消失。** ⇒ "壳退出 → 管道断开 → 内核自己退"这条路**本来就成立**，
  **那么第 12 条的通过就不能算作 `shutdown()` 生效的证据**。此时**必须**在
  `applicationWillTerminate` 里加一行日志（或临时 `print` 到 stderr）来**直接**证明它被调用了，
  再把那句话连同第 12 条的结论一起写进验收记录。
- **情形 B：强杀后内核还在（`benagen-core` 仍有输出）。** ⇒ 说明"管道断开"这条兜底
  **指望不上**，第 12 条的通过**确实**来自 `shutdown()`。此时再等 5–8 秒看它是否自己退干净
  （内核收到 EOF 后要跑完 `Daemon::close()`，上界 5 秒），并把最终观测写下来。

> 为什么必须分清楚：规格 §5.4 明说那条兜底路径**不保证 aria2c 被关掉**
> （内核要跑完关闭流程才退，来不及就是"第二个先死、第三个没人管"）。
> 任务 4 的报告曾用"`osascript quit` 之后 `pgrep` 为空"作为"收尾闸门生效"的证据——
> 但那两种解释**它都成立**，所以那次的证据不成立。这一条就是补上那个对照。
>
> ⚠️ 强杀那一下之后 `~/Downloads/Benagen/.benagen-state.json` 可能停在最后一次落盘的状态
> （强杀不留遗言是**预期**的，不是缺陷）。清理：重新打开应用跑一次正常退出即可。

## 16. 🚩 **已知缺口 —— 本阶段有意不修，不是通过项**

> **记在这里是为了让验收的人知道它还在，不是让你去"验它通过"，更不是让你去修它。**

**现象**：**内核进程死掉后，如果用户不点任何东西，界面可以几小时没有任何提示**——
工具栏徽标还停在上次握手时的「引擎未启动」，而那是**误导性的**（看起来像"还没开始"，
实际是"已经死了"）。

**为什么本阶段不修**：规格 §5.3 是**拉模型**、计划把轮询频率定死了；
而"子进程退出"这条信号要传到 `AppModel` 的可观测状态，会**直接撞上全局约束 17**
（`CoreCalling` 恰好四个成员、不许加便捷方法）。这是**一次设计决定**，
不该塞进修复轮里顺手做。

**验收时怎么做**：**不要**把它当失败来修，也**不要因为它而卡住交付**——
记录下来、在交付说明里如实写明，留给后续阶段。
（最省的修法方向：`Process.terminationHandler` 观测子进程退出，覆盖"死"这一类；
"卡住"那一类才需要低频探活。）

> **先后关系**：**先修 SIGPIPE**（`ProcessChannel.init` 里那句 `signal(SIGPIPE, SIG_IGN)`）。
> 在内核一死应用就消失的情况下，这条路根本轮不到"横幅不出"。

### 16b. 已知限制：把下载目录放在**网络盘**上会让界面明显变慢（Ruling D3 的复核结论）

> 与第 16 条同一个性质：**记在这里是为了让验收的人知道它还在，不是让你去"验它通过"，
> 更不是让你去修它。** 它是**阶段 D 的裁定 D3**在本阶段的**复核结论**（那条裁定原文就写着
> "下阶段若要做「可选下载目录」，这条要一起复核 —— 因为那正好会让用户有机会把目录指到
> 网络盘"；阶段 E 就是那个下阶段）。

**现象**：把下载目录（第 22 条）指到 NFS / SMB 这类**网络盘**上之后，进「文件」页、
取文件树、点「下载」会**卡顿**（网络慢时是秒级），同一时刻正在跑的下载、校验与落地监听
一起被拖慢。

**为什么**：内核在这三件事之前要做一次**廉价的磁盘核对**（把 `complete` 里"盘上已经不
满足完整性"的路径摘掉），而它在**持着内核锁**的情况下对 `complete` 里每个路径做一次
`stat`（`core/src/main.rs` 的 `recheck_complete_on_disk`）。本地盘上 1 万个文件约 20–40 ms，
**网络盘上的 `stat` 是秒级**。

**为什么本阶段不修**（复核结论：**仍然接受**）：
① 默认目录仍是本地路径；② 移出锁要三段式（锁内认领 → 锁外算 → 锁内装），
而那**正是** `ensure_complete` 已经在用的复杂机制 —— 为一个未观测到的场景再加一层，
与 C14/C15/C17 的教训相反；③ 它的失效形态是**变慢**，不是**变错**。

**已经做了什么**：把这件事**写到用户看得见的地方** —— 设置窗口那一段的脚注
（`DownloadDirectory.sectionNote`：**请选本机磁盘**）与本节。
内核代码**一个字都没改**（那是裁定要求的）。

**验收时怎么做**：**不要**把它当失败来修，也**不要**为此去改内核。按第 22 条验的时候
用**本机磁盘**上的目录即可；把这一段如实记录到交付说明里。

## 18. 主窗口关掉之后必须能回来

**做法**：打包 → 打开 → 等它加载完一批 → **点窗口左上角的红叉关掉窗口**
（应用仍在运行，Dock 里的点还在）→ 按下面各条各试一次。

**通过**：
1. **点 Dock 图标** → 主窗口回来，而且**直接是已加载的状态**（能看到文件列表），
   **不是**空态页、**不是**转圈。
2. **⌘0**（或「窗口」菜单 →「显示主窗口」）→ 同上。
3. 关掉之后再开一次，窗口里**不得**出现「正在加载交付清单…」的转圈。
4. 🚩 **「关于」或「设置」窗口在屏上时，关掉主窗口，再点 Dock ⇒ 当前什么都不会发生**
   （**已知缺口，本阶段有意不修，见第 16 条的口径**）。
   原因：判据 `anyVisibleWindow` 只认「**任意一个**可见窗口」（`App.swift` 的
   `AppDelegate.anyVisibleWindow`），而「关于」/「设置」窗口在屏上时它就是 `true`
   ⇒ `shouldOpenMain` 为 `false` ⇒ 不请求重开。
   **这一格下面第 1–3 条覆盖不到，而且它是最容易在日常使用里撞到的一种**：
   用户开着关于窗口、关掉主窗口、点 Dock，看到的是"点了没反应"。
   这一条现在只能靠人眼验，所以必须**真的试一遍**再判通过。
5. **应用已经在前台时点 Dock**（而不是先 `⌘Tab` 切走）→ 与第 1 条同样的期望：
   主窗口回来（这条走的是同一个 `applicationDidBecomeActive`，但"应用已活跃"时
   AppKit 不一定会再发这个回调——所以它与第 1 条不是同一条路）。
6. **点 Dock 重开 → 立刻点红叉关掉 → 再点 Dock**（账本 C17 那条可达序列）→
   主窗口**必须再次回来**。这一串中间**没有任何"有窗口在屏"的激活**，所以
   `noteWindowOnScreen()` 那条解除点走不到——只有 `MainWindowBridge.onAppear`
   里那次解除能救它。**这一格是第 2 轮修复栽掉、第 3 轮修回来的那条路**，
   状态机那一半现在有单测（`MainWindowReopenGateTests` 里那条同名序列），
   但"AppKit 回调真的送到了吗"只有人能验。

**不通过的样子**：点了 Dock 什么都没发生；或者窗口回来了但停在空态页转圈
（后者说明启动幂等那条没生效——那是同一个缺陷的另一半）。
**另外**：一次点击**开出两个**主窗口也是不通过（那是互锁那条线，
`MainWindowReopenGateTests` 的反向用例守着它的状态机那一半）。

## 19. 换交付码

**做法**：加载批次 A → 工具栏点那颗写着当前码的按钮 → 输入批次 B 的码 → 「加载」。

**通过**：
1. 工具栏那句**看得见当前交付码**（不是只有一个图标）；
2. 换成 B 之后，文件页显示 B 的树、面包屑回到根、勾选面清空；
3. **故意输一个不存在的码** → 面板里出现内核原文，**关掉面板之后 A 批次原样还在**
   （这是最要紧的一条：失败不得把当前批次弄丢）。
4. **点「加载」之后立刻点「取消」**（面板关掉、而请求照跑）→ 主区顶部必须出现一行结果：
   失败时是**内核原文逐字**，成功时是「已换到批次 B」。
   **这一行要活过面板**（收起它靠它自己的 ×，不是靠关面板）——「取消」那颗按钮
   **有意不禁用**（面板关不关得掉，不该由一次网络请求决定），所以结果是靠这一行
   才不至于零痕迹的（失败方向 = 静默失效；成功方向 = "我按了取消、界面自己换了一批"）。
5. **粘一大段东西（超过 2 KiB）**进输入框 → 「加载」变灰，且输入框下方**明说**
   「交付码过长（超过 2 KiB）…」——**不是**只有一颗灰按钮（约束 4）。
   同样地，把「高级」里的自定义下载地址粘爆 → 那句说明在**收起分组**时也看得见。

## 19b. 本地删掉已下载的文件之后重新下载（阶段 D 修的这条）

**做法**（与人类伙伴报的那次症状逐字对齐）：

1. 加载一个批次 → 点「全部下载」→ 等它下完（「传输列表」里都结束、文件页状态都是「已完成」）；
2. **进「文件」页看一眼**（这一步是必须的：它会给内核那份"哪些文件已完整"的缓存盖章）；
3. 在访达里**把刚下载的文件删掉**（只删文件，别删别的东西）；
4. 回应用 → 点「全部下载」（勾选面仍为空）→ 记录看到什么；
5. 工具栏点那颗写着当前码的按钮 → **重新提交同一个码** → 「加载」→ 再看一遍界面。

**怎么看算通过**：

- **第 4 步**：不是"报错"就不错了 —— 内核在"没有待下载的"时回的是**成功**，
  界面出现的是「**没有需要下载的文件**」（或直接开始下载那几个缺的文件），
  而**不是**「没有匹配到任何文件」那句 `invalid_params`；
- **第 5 步（本阶段修的两条）**：
  1. 第 4 步若出现过任何一句**错误或结果**提示条，同码重载**成功之后它必须被收起** ——
     它不是"重载了**还是**报这个错"，而是"重载成功、那句旧结论已经过期"；
  2. 同码重载之后，文件页的**勾选面按内核刚算出来的 `default_selected` 重播**
     （缺的那几个文件被勾上、底栏的「已选 N 项」跟着变）—— 不是"看着什么都没发生"。

**第 5b 步（关键的一条边界 —— 复审重要 2）**：在第 5 步之前，**先双击进到一个子目录**
（比如 `PFX/sub/`），然后**再**做第 5 步。

- **通过**：重载之后勾选面被重播，但**你仍然待在刚才那个子目录里**（面包屑没变）。
- **不通过**：重载把浏览位置打回了根目录 —— 那是**非用户动作**（内核恢复 / 重试同一个码）
  引发的用户可见状态改写，界面上没有一句话说明，用户攒了半天的位置会凭空消失。
- ⚠️ **换批**（第 6 步：换一个**不同**的码）**必须**回到根目录 —— 那是**另一棵树**，
  回到一个确定的落点是对的。所以这一条要**两种情形分别看**：同码=不回根，换码=回根。

> ⚠️ **第 5/5b 条的守卫是"纯值单测 + 代码审阅"，不是这一页的手工点击**（视图不单测，约束 8）：
> 判据在 `AppModel.loadGeneration`（**整次加载（含 `get_tree`）成功**才推进一代；
> 同码重载也推进；失败不推进）、`ManifestTracking.seed(generation:)` 的返回值
> `ManifestSeeding`（`selection` + **`isANewBatch`**）、`BrowserSelection.taskKey(...generation:)`
> 与 `EnqueueFeedback.of` 上，各有单测钉着。手工点这一遍是**端到端的确认**，
> 点不出来时先去看那四处。
> ⚠️ 视图侧那几行接线（`RootView` 的 `.onChange(of: model.loadGeneration)`、
> `FileBrowser` 的 `taskKey` / `seed` / `seeding.isANewBatch` 那一个 `if`）**没有任何自动化测试能覆盖** ——
> 这是**本期唯一只能靠这一段手工验收的东西**，别跳过。

## 19c. 换码面板里的历史批次（阶段 E：记住用过的码、写备注、点一条直接切）

**背景**：人类伙伴的原话是「显示历史交付过的批次码，并加载这个批次码的时间，**可以直接通过
选择进行切换**，并且允许给这个批次码添加标签，方便记忆」。所以这一段的三件事是
**列出来 / 点一下切过去 / 写一句备注**，而备注是**一条自由文本**（不是多个短标签）。

**做法**：加载**至少两个不同的批次**（这样列表里才有东西可挑），然后工具栏点那颗写着当前码的
按钮打开换码面板，按下面每一条试一遍。

**通过**：

1. **列表出现了**：面板里有一段「历史批次」，每条一行、**最近用的在最上面**；
   每行写着 `备注（没写备注时显示码本身）` + `码` + `上次使用时间`。
   - 时间的样子与侧边栏的有效期**同一副面孔**（`2026-09-18 09:12`，`+08:00` 同形、
     不带秒）—— 壳**没有**为历史另造一套时间格式。
2. **点一行 = 直接切过去**：点某一条的**文字部分**（备注/码/时间那两块），面板里**不出现**
   任何"已填入输入框"的中间态 —— 它**直接开始加载那一批**，成功后面板自己关掉、
   文件页显示那一批的树。
   - ⚠️ **这不是"填进输入框再点加载"**：输入框**一个字都不会被改动**。
     判据就是——点完之后输入框里仍然是原来那个码，而批次已经换了。
3. **备注重启后仍在**（这一条只有人能验）：在某一条的「备注」框里敲一句（例如
   `客户张三 / 9月肿瘤数据`）→ 敲**回车**、或者**点面板里的别处让焦点离开** →
   **退出应用、重新打开** → 打开换码面板 → 那句备注还在**原来那一行**上，
   而且这一行的标题显示的就是这句备注（不再是码）。
   - ⚠️ 两条路都要试：只敲回车、只点别处各一次。**焦点离开也算提交** ——
     只认回车的话，敲完直接去点另一行的那句备注会**无声地丢掉**。
   - 想自己核对形状，可以直接看文件：
     `~/Library/Application Support/BenagenDownloader/history.json`
     （`{"version":1,"entries":[{"code":…,"note":…,"base_url":…,"last_used_at":…}]}`）。
   - 备注里的**换行会被折成一个空格**（它是"一句"自由文本）、**首尾空白会被去掉**、
     内部原有的空格**一个都不动**。
4. **备注为空时的显示**：把某一条的备注**清空**（敲回车提交空串）→ 它的标题**回落到码本身**
   （不是一行空白）。手改 `history.json` 把 `note` 写成 `"   "`（纯空白）也一样回落到码 ——
   **一行"看起来是空的"标题在界面上与"这一行坏了"分不开**。
5. **列表为空时这一段不出现**：**同时**清掉下面这两个文件，再重启应用：

   ```
   ~/Library/Application Support/BenagenDownloader/history.json   # 壳的历史
   ~/Library/Application Support/BenagenDownloader/last_code      # 内核记的那个码
   ```

   打开换码面板 → **完全没有**「历史批次」这一段，也没有一个空盒子。
   输入框照旧可用（第 6 条）。

   ⚠️⚠️ **为什么两个都要删 —— 只删 `history.json` 会得到"一行记录"，那不是失败**：
   壳的历史为空时，`AppModel.rememberedCode()` 会读**内核的** `last_code` 当**一次性种子**
   并**立刻就把它写进历史**（规格 §1.3 / E-4；`AppModel.swift` 的 `rememberedCode()`，
   **先落盘再加载**）。而本节的**做法**里已经要求"先加载至少两个不同的批次"，
   所以 `last_code` **必然非空** ⇒ 面板上会出现**一行种子记录**。
   那不是"空列表这一段没藏住"，而是**历史已经不空了**，代码是对的。
   反过来说这条的准确表述是：**只有历史与 `last_code` 都空时，这一段才整段消失**。
   （`last_code` 就在内核的 `settings.json` 旁边 —— `core/src/main.rs:194-197` 取
   `settings_path.parent()/last_code`，而壳不传 `--settings`，所以走
   `core/src/settings.rs:199-208` 的默认目录，与壳的历史**同一个文件夹**。）
6. **输入框与历史列表并存**：在一个**新**码上手动输入 → 「加载」照旧成功 ——
   历史是**快捷方式，不是替代品**；成功之后这个新码**也进了历史**（排在第一条）。
7. **自定义交付服务器的那一条要问对服务器**（阶段 C 的 Ruling C10 记下的那个坑，
   本阶段由历史来填）：用空态页「高级」里的自定义下载地址加载过一批之后，
   **再从历史里点那一条** —— 它必须**仍然**去问那台自定义服务器并加载成功。
   - **不通过的样子**：去问了默认服务器，于是回一句"码不存在"之类的失败，
     而用户刚刚明明看见它列在历史里。
   - 判据在 `BatchHistoryEntry.baseURL` / `BatchHistoryRow.baseURLOrNil`（有单测）；
     视图侧那一句传参在 `SwitchDeliverySheet.switchTo(_:)`，**人眼只能在这一条里验到**。
8. **过长的码点不动**：手改 `history.json`，把某条的 `code` 换成几千个字符 →
   那一行**变灰**、悬停会说明原因（内核不会为一条超限的请求报错，它只把客户端**静默堵死**）。
   - 那一行的码是**中间截断**的一行等宽字（不是折成一大坨），因为它是几千个字符；
     悬停在那串码上能看到**全部原文**。⚠️ 变灰是**行为**上的（点不动），
     观感上还多一层截断 —— 别把"它还显示着一长串"读成"没挡住"。
9. **历史写盘失败必须说出来**（最终审查重要 1；这一条**只有人能验**）：
   把历史文件所在的**目录**改成不可写（去掉写权限就够了 ——
   `JsonFileStore` 是"先写临时文件再改名"，所以卡住它的是**目录**的写权限，不是文件的）：

   ```bash
   chmod 500 ~/Library/Application\ Support/BenagenDownloader
   ```

   然后在换码面板里给某一条写一句备注（回车提交）。
   - **通过**（两处都要看到）：
     ① 面板里**就地**出现一行警告「历史记录写入失败：…」（带系统给的原因）；
     ② **把面板关掉**（「取消」/ Esc）→ **主区顶部那一行还在** ——
        它不是说给面板听的，是"这句话必须活过面板"；
     ③ 两处那颗 `×` 都能收起它。
   - 恢复现场再验一次：`chmod 700 ~/Library/Application\ Support/BenagenDownloader`
     → 再写一次备注 → **那一行自己消失**（一次成功的写盘会清掉它，不必手动收）。
   - **不通过的样子**：敲完备注、写盘失败、应用**一个字都不说** —— 重启之后备注不见了，
     而且**无从归因**（这正是修复前的情形：注释承诺了落点，实现里没有任何视图读它）。
10. **自动加载失败之后点「重试」要去问同一台服务器**（Ruling E2①，本修复波顺手 1）：
    在空态页「高级」里填一个**自定义下载地址** + 一个不存在的码 → 加载失败 →
    退出应用、重新打开（它会带着历史里那一条的地址**自动加载**、再次失败）→
    在空态页上点「重试」。
    - **通过**：重试去问的仍然是**那台自定义服务器**（失败原文与刚才那句同一个来源）。
    - **不通过的样子**：点一下重试，失败原文换成了**默认服务器**给的另一种说法 ——
      用户一个字都没改，问的机器却换了。
    - 判据在 `EmptyState.baseURLToLoad`：输入框为空时，地址与码**一起**回落到历史里
      **同一条**记录（用户敲的优先）。⚠️ 视图不单测，**只能在这一条里验**。
    - 顺带验**成对回落**：输入框里敲一个**新码**（「高级」留空）→ 发出去的必须是
      "新码 + 默认服务器"，**不许**把历史里那台自定义服务器的地址带上去。

> ⚠️ **纯值单测能覆盖到哪一半**（视图不单测是本项目的硬约束，所以这份分工要写清楚）：
> · `BatchHistoryRowTests` 钉 **第 1 / 4 / 5 / 8 条的"画出来是什么"**：行文本、备注为空时的
>   回落、时间复用 `TimestampPresentation`、顺序、`base_url` 的空串 ⇒ `nil`、超长码的判据；
> · `NoteDraftsTests` 钉 **第 3 条的"该不该写"那一半**：备注草稿的五条规则
>   （没草稿不写 / 没变不写 / 交完删草稿 / 草稿优先于现值 / 清空是一次真的改动 /
>   面板关闭时全部交出去）。**"什么时候提交"那一半在视图里，单测盖不到。**
> · `AppModelHistoryTests` 钉 **第 9 条的后半个**（写盘失败**必须落在
>   `historyWriteFailure` 上**、能被收起、成功时不留痕）。
>
> ⚠️ **没有任何自动化测试能覆盖的，至少是视图侧这几行接线**：
> 第 2 条（`switchTo` 的点击）、第 3 条的**时机**（`onSubmit` / 焦点变化 / `onDisappear`
> 三个点接没接上）、第 5 条的**渲染闸门**（`if !historyRows.isEmpty` —— 列表为空时这一段
> 整段不出现）、第 7 条（`switchTo` 传 `baseURL`）、第 9 条的两处落点接没接上、
> 第 10 条的回落（`baseURLToLoad` 在 `load()` 里传对了没有）。
> 这几处**只能靠这一页**。
> ⚠️ 说"至少"不是含糊（最终审查顺手 8）：上面这几条是**今天数出来的**，
> 而这一类接线的清单**只会变长**（每加一条提示/一个回落就多一处）——
> 写成"只有这三处"会让人以为这是一份**完整**的清单，从而下一次漏验。

## 20. 文件页的选择（这一条只有人能验，视图不单测）

**做法**：加载一批 → 在文件页按下面每一条试一遍。

**通过**：
1. **单击任意一行** → 它**真的**被选中（行有高亮，最左边的方框变成打勾）；
2. 点那**方框** → 只切换这一行（其他行不受影响）；
3. **⌘ 点击**两行、**⇧ 点击**一片 → 多选成立；底栏「已选 N 项 · 合计…」跟着变；
4. **⌘A** → 全选**当前这一层**；
5. 底栏点「全选」→ 整批全部文件被勾上（底栏显示项数）；
6. **一项都不勾**时底栏**明说**「未勾选任何项，将下载全部待下载文件」；
7. 勾一个**目录**行 → 下载 → 传输列表里出现该目录下的**全部**文件；
8. 勾几个文件 → 「下载选中」→ 只有这几个进了传输列表；
9. **双击目录** → 进入；**双击文件** → 该文件进下载队列；
10. 右键任意一行 → 菜单里有「下载选中项 / 全选本层 / 全不选」；
11. 🔴 **双击进目录之后，底栏的「已选 N 项」不许自己涨**（2026-09-20 客户现场那条 bug）：
    在做第 9 条之前先看一眼底栏 → 双击进目录 → **再看一眼**：数字必须**一个字都没变**；
    连进两层也一样。然后随便勾**一个**文件 → 「下载选中」⇒ 传输列表里**只**该出现那一个文件
    （**不许**出现那一层的其他文件）。
    ⚠️ 这一条**只能靠这一行文字验收** —— 它的成因在 `List` 的选中行为与内核的目录前缀展开之间，
    纯值单测按构造抓不到（`BrowserSelection.afterEntering` 那两条只钉住了"进去之后勾选面该变成什么"，
    钉不住"双击真的会把它写进去"这件事本身）。

> 🔴 **第 11 条是 2026-09-20 修掉的一个真实交付事故**（客户原话："选择单个文件，『下载选择』，
> 结果下载了整个目录的文件"）。成因链**每一步都单独看都是对的**，合起来才是错的：
> ① 双击的**第一下**在 `List` 里就是一次**单击选中**，于是那个目录的路径被写进了勾选面
> （这条在本文件里早写着：`FileBrowser` 的 `.contextMenu` 那段注释说"在 macOS 上，
> 双击前单击已经把它选出来了"）；② 换层时**不动勾选面**（那是有意的：进目录再返回，
> 用户攒的勾选不该被清掉）；③ 于是那个目录路径**永远留在**勾选面里，而且**看不见**
> （它属于用户已经离开的那一层）；④ 内核把每个 `path` 当**前缀**展开
> （`core/src/main.rs` 的 `resolve_targets`）⇒ 整个目录都被下了。
> 客户看到的就是"底栏明明写着『已选 2 项』，下来一堆文件"。
> 修法：进目录时把**被进入的那一个**摘掉（精确匹配，不是前缀 —— 用户勾在里面的文件要留着）。
> 完整经过、判据与代价见 `BrowserSelection.afterEntering`。

**⚠️ 若第 2 条不通过**（点方框干扰了多选）：把复选框改成**纯指示器** ——
把那个 `Button` 换成裸 `Image`（去掉 `action` 与 `.help`），行点击仍是唯一的勾选方式。
这是**预先写死的降级**，不要临场发明别的。

## 22. 可选下载目录（阶段 E：默认仍是「下载」，可以在设置里改）

**背景**：人类伙伴的原话是「允许在下载的时候，选择下载到指定目录，默认是当前使用的"下载"目录，
可以在设置中进行配置」。生效方式是他选定的：**立即重启内核 + 明确提示**。

**为什么只能重启**：下载目录是内核的**启动参数**（`--download-dir`，`core/src/main.rs:1678`），
协议里**没有**这个键（`set_settings` 的类型化 `Settings` 只有七个数值键，
`core/src/settings.rs:32-47`）—— 所以"改目录"这件事只能是"换一个内核进程"。

**做法**：⌘, 打开设置 → 最上面那一段「下载目录」。

**通过**：

1. **默认状态（没配过）**：那一段显示「默认（~/Downloads/Benagen，由内核决定）」，
   「恢复默认」是**灰的**。「选择…」可用。
   - 那一段的脚注里还写着「请尽量选**本机磁盘**上的目录：网络盘（NFS / SMB）会让界面
     明显变慢」—— 那是 Ruling D3 的复核结论（见第 16b 条），别在改文案时把它删掉。
   - 判据（命令行取证）：**内核的 argv 里根本没有 `--download-dir` 这个 flag** ——
     ```
     ps -Ao command | grep benagen-core | grep -v grep
     ```
     输出里只有 `benagen-core`（`--download-dir` 一个字都没有）。
     ⚠️ 这与"传一个和内核默认值一样的路径"是**两件不同的事**：后者在内核哪天改默认值时
     会让壳把用户悄悄带回老地方（E-5 明禁的静默分叉）。
2. **改目录的确认框必须把三条后果说全**：点「选择…」挑一个新文件夹（例如 `~/Desktop/交付测试`）
   → 弹出的确认框里逐条写着：**① 正在跑的任务会停**（内核重启）；
   **② 新目录里没有记录的文件会重新校验**；**③ 旧目录里的文件不会被删、也不会被搬走**。
   - ⚠️ 第 ② 条**不能**读成"所有文件都会重新校验"：**换回旧目录**那种情形里，
     那个目录里已经有一份 `.benagen-state.json`，内核会把状态读回来、一个字节都不用重校验。
   - 点「取消」⇒ **什么都不发生**（内核不重启、偏好不落盘）。
3. **确认之后**（这一条是整段的重点，需要两个终端窗口取证）：
   - 先在一个终端里盯着旧目录：`ls -la ~/Downloads/Benagen | wc -l`（记下数字）；
   - 确认改目录 → 内核被重启 → **新目录里出现了 `.benagen-state.json`**
     （`ls -la ~/Desktop/交付测试`）；旧目录里的文件**一个都没少**（同样的 `ls | wc -l`，
     数字不变，且没有 `.benagen-state.json` 被删/被搬走的痕迹）；
   - 命令行再取证一次 argv：`ps -Ao command | grep benagen-core | grep -v grep`
     —— 这一次必须有 `--download-dir /Users/<你>/Desktop/交付测试`。
3b. **回执必须活过设置窗口**（最终审查重要 2）：确认之后**把设置窗口关掉**（⌘W）→
   **主区顶部仍然挂着那一行回执**（成功：`下载目录已改为 …（内核已按新目录重启）`；
   失败：`内核重启失败：…` 或 `内核还在重启中，这一次没有改成…`）→ 点它自己的 `×` 才收起。
   - **为什么这条要单列**：改之前这份回执是设置窗口里的一个 `@State`，**窗口一关就没了**。
     而"重启被一次在飞的重启挡住 ⇒ **这一次没改成**"那一格说的事情是——
     **内存与盘上都是新目录、内核还在旧目录上跑**，回执是**唯一**的提示。
     窗口关掉之后就变成"设置里显示新目录、引擎横幅是绿的、没有任何东西再说这件事"，
     用户会在整个会话里以为文件下到新目录去了。
   - **不通过的样子**：关掉窗口再回到主区，顶部什么都没有；而内核的 argv 里还是旧目录
     （`ps -Ao command | grep benagen-core`）。

3c. 🚩 **回执的高度不许跟着路径长短变**（阶段 E 修复波：一次真实的布局事故）。
   **这一条只有人能验**（视图不单测），而且判据是"**底部的两样东西还在不在**"：
   - 选一个**很深的目录**当下载目录（例如先手工建出
     `~/Desktop/交付测试/再深一层/依然更深/还要更深/最后一层`，在面板里选**最里面那一层**）
     → 确认 → 内核按新目录重启；
   - **通过**：主区顶部那条回执是**两行** —— 第一行是固定那句
     「下载目录已改（内核已按新目录重启）」，第二行是路径（**一行**，
     太长时中间显示 `…`，**鼠标悬停能看到完整路径**）；
     同时 **文件页底部的「全选 / 全不选 / 下载选中」那一栏还在**、
     **左侧边栏的「批次摘要」也还在**（这两样都锚在窗口内容的底边，是这次事故的现场）。
   - **两行、且路径必须在第二行**：第一行**一个字都不许出现路径**（不许并回一句 ——
     那次事故就是"整句一行铺开"造成的）。判别式：把窗口缩到最小宽度，
     第一行**依然是固定那句**、高度不变，长的部分只在第二行被中间截断。
   - **不溢出的常驻行上不该有滚动条、也不该吞滚轮事件**（⚠️ 这条**只能人眼验**，
     是本阶段唯一没有实测兜底的一点）：常驻行现在**恒有一个 `ScrollView`**
     （高度封顶用的），短内容时它与内容等高、没有可滚的距离。
     验法：让主区正常显示（顶部只有一条一行的横幅，或干脆没有横幅）→
     **① 左右两侧不该出现滚动条**（系统设置里把"显示滚动条"改成**始终**也要看一眼）；
     **② 鼠标停在那条常驻行上滚滚轮 → 主区的文件列表应当照常滚动**
     （若被吃掉，说明那块滚动区把事件截了 —— 那就是要报的缺陷）。
   - **不通过的样子**（= 修复前的人类伙伴原话）：界面排版变了，最下方那一栏**整条不见**、
     侧边栏的批次摘要**超出软件界面看不到**；**把窗口拉高**或者点「恢复默认」就恢复。
     ⚠️ 见到这个形态先怀疑"**有常驻提示行的高度被外部文本撑起来了**"
     （判据与理由在 `macos/Sources/BenagenDownloader/Views/RootView.swift` 文件头那段 ——
     常驻提示行的高度不许由外部文本 / 外部数据决定），而不是"窗口跑到屏幕外"—— 判别式：
     **整体拖动窗口没用、拉高有用**。
   - **图标与 × 要贴着第一行**（第 3 轮修的回归）：多行正文时它们**不许掉到内容底边**
     （一度就是这样：差 16pt 以上，一眼能看出坏）。验法：让某条常驻行显示**多行**正文
     （例如把内核二进制挪走再点「重试」），看图标是否与**第一行**齐平。
   - 同一个判据也适用于其余常驻行：内核横幅（`engineBannerBar`，它的原文里可能带
     三行候选路径）、换码结果（`switchOutcomeBar`）、历史写盘失败
     （`historyWriteFailureBar`）、下载回执里那串**逐条拒绝理由**
     （条数由内核决定，磁盘满那类整批性故障一次能回几千条）。
   - **机制**（`Views/ResidentNotice.swift`）：散文正文**放得下按自然高显示、
     放不下就钉在 48pt 上可滚动**（列表那一档 80pt）—— 高度**永远**与外部文本/数据的
     长度无关，但**全文/全部条目都在**、可滚动、可选中复制（约束 3/4/C-7）。
     ⚠️ 这里**不用 `lineLimit` 截断**：多行的内核原文只显示前几行就等于把失败原因砍掉。
   - **设置窗口里那一段也是同一个现场**（第 2 轮修的）：它显示同一条回执
     （含完整路径）、窗口还更窄 —— 现在两处共用同一个 `DownloadDirChangeNotice`。

4. **重启之后界面反映"新目录是空的"**（不能显示一批"已完成"的假象）：
   改目录之前先加载一批、下几个文件（传输列表里有"已完成"）；
   改目录并确认之后 —— 传输列表**空**（新内核手里没有引擎任务）、
   文件页的状态列回到"未下载/待下载"。**不允许**出现"清单还是那批、状态还标着已完成"。
   - 这一条正是阶段 D 修掉的那类缺陷；它由重启流程里那次"自动重新加载当前批次"保证
     （`restartKernel` 的 `performLoadDelivery(code: loadedCode, …)`）。
5. **「在访达中显示」跟着走**（阶段 E 顺手补的一条接线）：换到新目录、下完一个文件 →
   传输列表里右键「在访达中显示」→ Finder 定位到**新目录里**那个文件。
   - **不通过的样子**：Finder 打开了、但定位到 `~/Downloads/Benagen/...` 下一个不存在的
     文件（那个按钮看起来点得动、其实什么都没发生 —— 约束 4 明禁的静默失效）。
6. **不可用的目录在确认框之前就被拦下**：选一个**只读**的文件夹（或者在面板里选一个
   **普通文件**的路径、或一个已被删掉的路径）→ 弹的是「这个文件夹不能用」+ 那句原因
   （路径原文在里面），**只有「知道了」一颗按钮**。
   - ⚠️ 判据是**内核没有被重启**：那一刻 `ps` 里的 `benagen-core` 进程号与之前一模一样。
7. **选同一个目录 = 什么都不做**：把「选择…」指到**已经在用**的那个目录 → 确认之后
   回执写着「下载目录没有变化，没有重启内核」，且 `ps` 里的内核进程号**没变**
   （正在跑的任务一个都没停）。
8. **重启应用之后仍然生效**：⌘Q 退出 → 重新打开 → 设置里显示的还是那个新目录，
   而且 `ps` 里的 argv 里有 `--download-dir`。文件形状可以直接看：
   `~/Library/Application Support/BenagenDownloader/preferences.json`
   （`{"version":1,"download_dir":"/abs/path"}`；点「恢复默认」之后是
   `{"version":1,"download_dir":""}`）。
9. **「恢复默认」**：点它 → 同样的确认框 → 确认 → 回执是「已恢复默认下载目录…」，
   `preferences.json` 里 `download_dir` 变回空串，内核的 argv 里**又没有**
   `--download-dir` 了（回到第 1 条的形态）。
10. **坏文件不影响启动**（E-1 的现场验证，不能只靠单测）：退出应用 →
    把 `preferences.json` 内容改成一段乱码（例如 `not json at all`）→ 重新打开应用 →
    **应用照常起来**、设置里显示「默认（…）」（= 当未配置），没有任何报错弹窗。
    - 同样的三份乱码也要试：`{"version":99,...}`（不认识的版本）、`[1,2,3]`（顶层不是对象）、

## 23. 详细日志与导出诊断日志（2026-10-06）

客户报「下载引擎已断开」「一直转圈」时，**先要日志再谈别的**。这一节说清楚三件事：
怎么开、怎么导、导出来长什么样。与 Windows 那一侧是**同一套语义**（同一张字段表、
同一个目录名前缀、同一句隐私提醒），差别只在入口的壳不同。

### 23a. 两份日志落在哪

| 谁写的 | 文件 | 位置 |
|---|---|---|
| 内核 | `diag-kernel.log` | `~/Library/Application Support/BenagenDownloader/` |
| 壳 | `diag-shell.log` | **同一个目录** |

**让客户交一个目录就够**（两者的家是同一个）。两份都是**有界**的：普通档单文件 1 MiB、
留一代（约 2 MiB）；详细档 4 MiB、留两代（约 12 MiB）。**永不无限增长**——
所以让客户"多跑几天再取"是安全的。

一行一条，形如 `ts=<unix 秒> event=<事件名> k=v …`；`ts` 是 **UTC 的 unix 秒**
（`date -r <ts>` 换算）。

### 23b. 怎么开

**⌘, → 设置 → 「详细日志」那颗勾选框**（在「下载目录」那一节下面）。

- 开了之后**每一次往返都记一行**：到 aria2 的每一次 JSON-RPC（`event=aria2_call`，
  失败那行带 aria2 自己说的原文）、壳到内核的每一次调用（`event=kernel_call`）。
- 🔴 **改了会立刻重启内核**（正在跑的任务会停）—— 那句话就写在勾选框下面。
  级别走的是内核的启动参数 `--log-level verbose`，只有重启才生效。
  **复现问题之前就打开**，不要等出事了再开。
- ⚠️ **壳自己那一份不重启也跟着变**：勾上的那一刻 `diag-shell.log` 当场开始记详细档
  （壳这个进程不重启，它的级别是就地落的）⇒ "应用还开着、内核刚重启完"那个中间态
  是**预期**。
- 关掉之后内核的 argv 里**不再有 `--log-level`**（**不是**拼一个 `normal`——缺省即普通档）。
- 普通档**与加这一档之前一字不变**。

### 23c. 怎么导

**⌘, → 设置 → 「导出诊断日志…」**（就在那个勾选框下面）→ 弹一个 `NSOpenPanel`
选文件夹 → 选一个目标文件夹 → 它**在里面新建一个时间戳子目录**再往里拷。
回执画在**同一节里按钮的下方**（含路径与那句隐私提醒），**导多少次都不会互相覆盖**。
用户取消 ⇒ 回执写着"取消"（**不是失败**）；失败 ⇒ 系统原文照登。

### 23d. 导出来的文件夹长什么样

```
你选的那个文件夹/
└── 诊断日志-20261006-093011/     ← 时间戳是 UTC（YYYYMMDD-HHMMSS）
    ├── diag-kernel.log           ← 存在的那几份：内核在前、代次由新到旧
    ├── diag-kernel.log.1
    ├── diag-kernel.log.2
    ├── diag-shell.log
    ├── diag-shell.log.1
    ├── diag-shell.log.2
    └── 说明.txt                  ← 那个文件夹里唯一一份不是日志的文件
```

- **只拷真的存在的那几份**（普通档通常只有一份内核 + 一份壳，`.1`/`.2` 在详细档才会出现）。
  没产生过的**不会**造一个空文件出来，也不算失败。
- `说明.txt` 是这份导出的**清单**，不是日志内容。七格头（应用版本 / 内嵌内核的 `sha256` /
  协议版本 / **`log_level:` —— 本次是哪个档** / 系统与版本 / 架构 / 导出时刻）+
  每份日志的**字节数 + `sha256` + 覆盖时间范围**，没产生的那几份逐行写「尚未产生」。
  ⇒ **`log_level:` 那一行是核对"我到底开没开详细档"的唯一入口。**
- ⚠️ **字段表与 Windows 那一侧逐字相同**（那是一条跨端契约），但**两处 sha256 的来源不同**：
  Windows 的内核 `sha256` 是**编译期常量**（内嵌内核时算好的），macOS 是**导出时现算**
  那个内核文件的 sha256；取不到时那一格如实写"取不到"，**不编一个哈希**。
- **没有压缩包、也没有加锁**：导出时日志可能仍在被写，某一份的最后一行可能是写到一半的。

⚠️ **隐私（规格 §2.7，两端同一句）**：**这份日志可能包含下载地址片段** ——
详细档把 aria2 的原始报错**原样**落盘，而它可能带上下载地址。我们**没有做自动过滤**
（要可靠地抹掉它得先能识别它，而任意第三方文案识别不了；做一个不可靠的过滤器比不做更糟）。
**发送之前，你可以自己打开看一眼。** 本来就不记的：交付码本身、文件路径本身、`rpc-secret`、
客户的目录名。
（其中**交付码与下载目录**在写进日志之前会被**按字面**抹成 `[已隐去]` —— 壳知道那两个串
（码在它刚发出去的请求里、目录在它自己存的偏好里），落点是 `CoreClient.setRedactions`
（调用点 `AppModel.rememberRedactions`）。⚠️ **抹不掉的剩下两种**：
① 第三方文案里以**别的写法**出现的那些片段（换大小写、URL 编码、被拆开）—— 那不是"忘了做"，
是 §2.7 论证过的做不到；
② **没有配置下载目录时（默认就是这个状态）内核自己那条默认路径** —— 壳推下去的是空串
（`DiagnosticsLog.redact` 跳过它）、也不传 `--download-dir`，内核于是回落到**它自己**的默认路径
（`core/src/paths.rs`：`~/Downloads/Benagen`），而那个串出现在内核 `preflight` 的失败文案里时
是**逐字落的**（`core/src/main.rs`：`目标目录不可写（{dir}）`）⇒ 壳**不知道**它，抹不掉
（本仓的 `kernelDefaultDisplayPath` 明说了它只是显示用的）。**行为是对的**（猜一条客户机上的
路径去抹比不抹更糟）；错的是把"下载目录会被抹掉"说成无条件的。）

> ⚠️ **上面那句"本来就不记的"在 2026-10-06 之前是一句绝对句，而它是假的**（终审实测，
>   与 Windows 那一侧同一件事）：交付码是**我们自己**拼进内核文案里的
>   （`core/src/delivery.rs` 那条 404 的 `…/{交付码}/manifest.json`），
>   `core/src/main.rs` 的 `preflight` 同样带着客户目录名 —— 两者都经 RPC 错误体流进壳日志
>   那一行的 `why`，而 `why` 是逐字落的。同一天被这条打假的还有 `说明.txt` 自己那句
>   （已改成上面这个口径）与三份日志器的模块头。
>
> ⚠️ **上面那段本身在修复轮 2 又被收窄过一次**：原来它只列了"第三方写法"一种抹不掉的，
>   而**默认配置**（没设下载目录）下内核那条默认路径同样抹不掉 —— 见 ② 。

### 23e. 这一节里**本机验不了**的（如实记账）

- `NSOpenPanel` 真的打开、真的能选目录、文件真的写进去了 —— **没有自动化判据**
  （导出那一段是 `DiagnosticsExport` 的纯逻辑 + 一次系统对话框）。
- 导出的文件夹里 `说明.txt` 两处 sha256 与外面那份文件**真的对得上**。
- **详细档真的能抓住一次"引擎不回话"** —— 这条只有等下一次现场。
- **详细档开着对下载速度的影响**（规格 §8 R4，本轮没有量）。

> 判据那一半覆盖到哪：`DiagnosticsExportTests`（时间戳目录名含闰日 / 字段表逐行 /
> 只列存在的文件）、`AppModelVerboseLoggingTests`（开关那条链：重启出来的内核拿到新的
> `--log-level`、同值不重启、写盘失败不动内核）、`DiagnosticsLogTests`（壳那份日志器的
> 有界与轮转），以及 `CoreClientTests` / `DownloadDirectoryTests` 里那几处
> `coreArguments` 的拼装；**视图不单测**是本项目的硬约束。

## 附 D. 2026-09-20：macOS 13 适配这一轮（交付记账）

**起因**：客户在 **macOS 13.7.8 Intel**（2017 代，封顶就是 13）上双击
`BenagenDownloader-Intel.dmg` 里的 app，得到「应用程序的这个版本不能与此版本的 macOS 配合使用」。
⚠️ 事故之前本机的完整 e2e 是**全绿**的、Intel `.app` 也**真起过窗口** ——
这一条就是「本机跑通 ≠ 真机能跑」的实证，别把它读成"当时没测"。

### 改了什么

`macos/` 只有**一份源码树**，架构只是同一份源码的编译输出，所以两个架构都受影响：

| 面 | 改动 |
| --- | --- |
| 下限 | `Package.swift` 的 `.macOS(.v14)` → `.v13`；`build_app_macos.sh` 的 `MIN_MACOS` → 13.0；aria2c 加 `-mmacosx-version-min=13.0` 并**两个架构都重编** |
| 模型层 | `AppModel`：`@Observable`（Observation 框架是 **14+**）→ `ObservableObject` + 19 个 `@Published`，**并加三处写护栏**（见下） |
| 视图层 | 10 处 `let model:` → `@ObservedObject`；6 处双参 `onChange` → 单参 / `.task(id:)` |
| 设置入口 | 新增 `Views/SettingsEntry.swift`：`SettingsLink`（14+）与 13 的 `showSettingsWindow:` —— 全仓**唯一一处** `#available` |
| 判据 | 新增 `check_minos_macos.sh`，接进两个打包脚本（见 §0b） |
| 资产 | 两个架构的 aria2c 重编（`minos 26.0` → `13.0`），`core/assets/` 与 `downloader/internal/engine/assets/` 两边同步，`ARIA2C_EMBED_SHA256` **两个字面量都换** |

⚠️ **为什么 ARM 那份也重出了**：不是"顺带"，是**必须**——`@Observable` → `ObservableObject`
这一步没有 Intel/ARM 之分。降下限本身对 ARM 无害（`minos 13.0` 的包在 macOS 26 上照跑），
但**失效粒度真的变了**（见下一条），所以 ARM 也重出并做了同样的回归。

### 三处写护栏（本轮唯一新增的运行时风险）

`@Observable` 对**等值**写入会**抑制**通知，`@Published` **不会**。而传输列表每 200 ms 轮询一次，
`fetchTransfers()` 每拍都会重写 `engine` ⇒ 换成 `@Published` 后会**凭空多出 5 Hz 的全局失效**。
所以三处加护栏：`if engine != .running`、`if lastError != nil`、`if protocolAlerts != fresh`
（最后一条顺带给 `ErrorBody` 加了 `Equatable`）。**这不是优化，是必需品** ——
反过来，`@Observable` 换成 `@Published` 却**不加**护栏，就是一次静默的性能回归。

### 两处必须记下来的事

**① 入库的 arm64 aria2c 一直停在 `-g` 那版 —— 本次重建才对齐。**
重编后 arm64 从 2 491 672 B 变成 2 135 848 B。这不是本次改动造成的：
`build_aria2_macos.sh` 的头部**早就算过这笔账**（"重跑本脚本得到的 arm64 与仓库里入库的那份
不会逐字节相同……剩下的体积差 **355 856 B** 是 `-g` 的调试信息，而它在 `__LINKEDIT` 里"），
只是那份资产**从来没被按 `-O2`（不带 `-g`）真正重出过**。本次实测差 **355 824 B**
（= 355 856 − 32，那 32 就是新加的版本串），与它预测的一致。

判定依据（本次实测）：`__text` 只差 24 字节（0xf6648 → 0xf6660）、`__TEXT` 段大小**一样**
（1 228 800）、`Configuration` **逐行相同**；差的全是 `nm -a` 里那 **216 条 `N_OSO`**
调试映射（旧的 26 887 行 → 新的 7 958 行）。⇒ **无行为差异**。
副作用是好的：入库资产第一次真正对齐了本脚本的开关，两个架构的资产也不再"不同代"了。
⚠️ 已把这条时效注记补进 `build_aria2_macos.sh` 的头部（免得将来有人跑 `nm -a`
看到 7 958 行误判成回归）。

**② 本机的 Little Snitch 会让 x86_64 的 e2e「偶发」在启动取证处失败。**
第一次 `e2e_shell_macos.sh x86_64` 以 `matched_windows=0` 中止；**同一棵树上重跑两次都通过**
（`matched_windows=1` 与 `=2`）。取证输出里能看到那条弹窗：

```
owner=Little Snitch Agent  title=Connection alert: BenagenDownloader via benagen-core
                                 wants to connect to download.benagen.com
```

成因：起真壳会**自动加载内核记住的交付码**（本脚本头部那段 ⚠️ 写的就是这件事）
⇒ 壳一启动就外联 `download.benagen.com` ⇒ 防火墙的连接弹窗抢在应用窗口之前。
`verify_app_launch_macos.sh` 是 `sleep 4` 之后**单次**取样、**不重试**，所以时序一偏就红。
⇒ **判定：本机环境造成的抖动，不是本次改动引入的回归**（同一份产物、同一条命令，2/3 通过）。
⚠️ 真机上若也装了防火墙，同理 —— 见到这条红先看有没有弹窗，别急着怀疑代码。

### 可重现性：写"哪一棵树 + 哪一份工具链 ⇒ 哪一个 sha256"，**不写"重跑会不会变"**

这是本轮专门查清的一件事，**旧的写法（"重出后 sha256 逐字相同 ⇒ 可重现"）已被推翻**。

1. ✅ **固定一棵树 + 同一份 cargo + 同一台构建机 + 同一组 `RUSTFLAGS`/PATH ⇒ 可逐字节重现。**
   依据：`854571f8…` 在**三次真重编**里逐字相同、`15bb8477…` 在**两次真重编**里逐字相同，
   而且**每一次的日志里都真有 `Compiling`**（构建前一律 `touch` 源文件强制重编）。
2. ⚠️ **"重跑一遍、sha256 没变"本身不是证据。** 源码 mtime 没变时 cargo **空转**，
   日志里只有 `Finished … in 0.30s / 0.07s / 0.16s`、**没有一行 `Compiling`** ——
   空转当然逐字相同，那什么都没证明。（旧那句就是这么来的。）
3. ⚠️ **改动源码会让字节变，连"不会被编进去的注释"也会。** 本轮实测一个**反直觉**的事实：
   **只改一行 `#[cfg(test)]` 模块里的注释** ⇒ **Linux** 那份字节就变
   （**−32 字节**、BuildID `9afbaa68…` → `f5fc2cc5…`、sha256 `15bb8477…` → `854571f8…`），
   而**同一改动下 macOS 两份的字节不变**。
   **机制未查明** —— 那行注释在 `#[cfg(test)]` 里、release 又不带 debuginfo，
   代码生成这一层解释不了它。照实记在这里，**不要当成结论去解释它**。
   ⇒ 实践含义：**切产物之后不要再动源码**，"改的只是注释"**不能**当作"字节没变"的理由。
4. ⚠️ **跨 cargo 不可类推。** 同一棵树、同一个脚本，macOS arm64 用 **rustup** 那份 cargo
   出 `7871968 / c40130f7…`，用 **Homebrew** 那份出 `7960944 / dd91cdcf…` ——
   **两次都退出码 0、都不告警**。**交付的那组是 rustup 那份**，
   所以复现要先 `export PATH="$HOME/.cargo/bin:$PATH"`。
   （Linux 那条路相反：脚本**强制**要求 rustup 那份，选错会在编译前就大声失败。）

## 附 G. 2026-09-30：DMG 里加「已损坏修复」脚本（交付记账）

### 为什么做

客户侧**经常**双击应用就提示「已损坏，无法打开」。根因是**包没有 Developer ID 签名**
（`build_app_macos.sh` 有意不做签名与公证）：从网络下载来的产物带 `com.apple.quarantine`，
Gatekeeper 拦下；而 macOS 15 起「右键 → 打开」那条放行路已被 Apple 移除（§0b 第 3 条）。

### 做了什么

盘里多放一件 **`已损坏修复.command`**（源码 `macos/Resources/已损坏修复.command`，
与三个品牌图标同一性质的**入库静态资产**；`build_dmg_macos.sh` 装盘时拷进去，
并在挂载自验里判「在不在」与「可不可执行」两条）。

客户双击它：找到应用（优先脚本旁边那张盘，其次 `/Applications`）→ `ditto` 装进
`/Applications` → `xattr -dr com.apple.quarantine` → **复查属性确实没了** → 启动。

**它有意的两处「不做」**（被参考的那张第三方 DMG 两件都做了）：

| 不做的 | 为什么 |
| --- | --- |
| `sudo spctl --master-disable` | 把**整台机器**的安全闸门永久关掉、不自动恢复。而且**没用** —— 见下 |
| `codesign --force --deep -s -` | 本包**本来就没有签名**；中途失败会留下**签名残缺**的包（arm64 上直接起不来）。Apple 也已弃用 `--deep` |

### 🔴 本轮最要紧的一条实测（「关掉 Gatekeeper 也一样」是错的）

同一台机器、两个**除隔离属性外完全相同**的假应用（同机 `spctl --status` 当时报
`assessments disabled`，即 Gatekeeper **关着**）：

| | `open` 退出码 | 实际起来了没 |
| --- | --- | --- |
| A：带 `com.apple.quarantine` | **0** | **没有** |
| B：不带 | 0 | 起来了 |

两条结论，都已落进脚本注释：

1. **清隔离属性才是真正起作用的那一下**；`spctl --master-disable` **替代不了它**。
2. **`open` 的退出码不能当作「启动成功」** —— 它照样返回 0。修复脚本因此改成
   **看进程**（`pgrep`），不看退出码。

### 本机验证读数（现取）

    ✓ 包结构完整（Info.plist 与可执行位都在 —— 这条抓的是「用 cp -R 拷坏了 bundle」）
